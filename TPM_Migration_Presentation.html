Raw OEE · Data migration

TPM migration:
SQL Server to PostgreSQL

A pipeline that copies 25 master_data tables and production_core.autodata from SQL Server (TPM_PGSQL) to PostgreSQL, one YAML mapping per table.

  • Plain copy with column mapping and lookups. No business changes.
  • Extract, transform in Polars, load with COPY.
  • Rehearsal by default: everything runs, then rolls back.
Anything that changes a production system needs testing and your normal change-control review first. Always run a rehearsal before a real migration.

2 · Extract

Read in chunks, in windows

Rows are read in chunks of 50,000 into a DataFrame. Only the columns the mapping uses are read. Small tables are read in one go. The big table, autodata, is read in windows of one logical month.

Terms

  • Window: one time range of autodata, loaded in one transaction.
  • Chunk: the next 50,000 rows read from inside a window.
  • Logical day: starts when the first shift starts (for example 06:00), from utility.get_logical_day.

Windows

window 1: 2026-10-01 06:00 -> 2026-11-01 06:00
window 2: 2026-11-01 06:00 -> 2026-12-01 06:00
each window starts where the last one ended

Fixed windows of N days are also possible (--days N).

A row belongs to the window that contains its start time (sttime). No gaps, no overlaps. Rows with sttime NULL get one extra window, so no row is lost. The run stops if the windows miss any row.
3 · Transform

Rules from the YAML file

Each DataFrame goes through the rules of its YAML mapping: copy, cast, trim, coalesce, map, lookup, and so on.

Lookup

A business id from the source (for example a machine code) is replaced by the target's iot_id, using the parent table already loaded in PostgreSQL.

Checks

  • The value fits the target type.
  • NOT NULL columns have a value.
  • No duplicate key.
  • The parent was found.
A row that fails a check is not dropped silently. It goes to reports/<table>_exceptions.csv with a reason. After every table: rows read = rows loaded + rows in the exceptions file, or the run stops.
3 · Transform

How is_icd is solved for autodata

autodata has two kinds of rows: cycles (datatype = 1, a part being machined) and downtimes (datatype = 2). A downtime is an ICD (in-cycle downtime) when it happens inside a cycle that ran longer than its own cycletime.

Rule: a downtime is ICD when a cycle of the same machine, with duration > cycletime, starts before the downtime starts and ends after the downtime ends.

SQL Server did this with a slow check per row. Here it is done in Polars with two frames per window. prod_icd_cycles means production cycles that can hold an ICD.

FrameWhat it holdsHow it is readHow often
Frame 1
prod_icd_cycles		 Only candidate cycles: datatype = 1 and duration > cycletime. Columns mc, sttime, ndtime. Includes cycles that started before the window start and run into it. extract_batch_prod_icd_cycles(window_start, window_end), one query per machine, range [window_start - lookback, window_end) Once per window
Frame 2
df		 The real rows to migrate (all datatypes): one chunk of up to 50,000 rows. extract_batches: SELECT ... WHERE sttime in the window, fetchmany(50000) Repeated until the window is done

lookback is the longest cycle that qualifies (measured once per run). No cycle that contains a downtime can start earlier than window_start - lookback, so Frame 1 stays small but is still exact.

3 · Transform · Why Polars

Idea 1: vectorized execution

Vectorized means one operation is applied to a whole column in one call, not to one value per call.

Row by row (we do not do this)

for row in rows:           # 50,000 times
    if row["mc"].lower().strip() == ...:
        ...

Polars expression (the pipeline)

key = pl.col("mc").str.to_lowercase().str.strip_chars_end()
batch.with_columns(key.alias("_mc"))   # all rows, one call
  • No interpreter overhead per row. A Python loop pays a cost on every iteration. Polars pays it once per column, then runs a compiled loop.
  • CPU-friendly. The loop runs over a plain array of numbers, so the CPU can use SIMD (one instruction on several values) and keep data in its fast cache.
3 · Transform · Why Polars

Idea 2: columnar, in-memory data

Polars stores data by column (the Apache Arrow layout), not by row.

Row layout:     [mc, sttime, ndtime] [mc, sttime, ndtime] [mc, sttime, ndtime] ...
Column layout:  mc:     [M1, M1, M2, ...]
                sttime: [06:00, 06:10, 06:12, ...]     <- one filter reads only this block
                ndtime: [06:05, 06:12, 06:30, ...]
  • A rule like sttime < ndtime reads only the two columns it needs.
  • Values of one type sit next to each other, so memory is read in long straight runs.
  • Each chunk is held in memory while transformed. No temporary table, no file on disk. extract asks SQL Server only for the columns the mapping uses.
Memory stays bounded. The pipeline never loads the whole 900,000-row table. It reads 50,000 rows at a time, transforms, loads, moves on. Only the window's cycle frame (prod_icd_cycles, three columns) is kept for the whole window.
3 · Transform · Why Polars

Ideas 3 and 4: many cores, and joins instead of lookups

Many cores, no Python lock

Python runs one thread at a time (the GIL). Polars runs in Rust and releases that lock, so one join or group_by can use all cores. No threading code is needed.

Lookups as one join

Row by row: one database query per row = 900,000 round trips.
Here: each master table is read once per run, then joined to every chunk. The join builds a hash table of the small side once.

machine_informationread ONCE per run
→
hash tableinterface_id → iot_id
←
chunk of 50,000 rowsjoin
→
chunk with machine_iot_id

is_icd as a set operation

The old SQL ran an EXISTS sub-query for every downtime row (minutes per window). add_is_icd instead:

  1. splits downtime rows and cycles by machine (partition_by);
  2. joins them with the range conditions (join_where: cycle starts before, ends after);
  3. marks all matches in one is_in operation (a hash-set test).

It also does less work: cycles are first filtered to the time range of the chunk's downtimes, and Frame 1 only holds cycles that can contain a downtime at all.

  • Polars removes the slow, CPU-heavy middle: casts, trims, lookups, duplicate checks and is_icd.
  • The first full real run read and loaded 913,753 autodata rows in about 2.5 minutes end to end (4 windows). This is a whole-pipeline number, not "Polars speed".
  • To go faster still, look at the database read and the COPY loop, not the transform.
  • The pipeline uses eager DataFrames on 50,000-row chunks because data arrives from a database cursor, not from a file. Lazy mode helps mostly for large file scans.
4 · Load

Complete or not at all

Normal table: one transaction
  1. target must be empty
  2. COPY all chunks
  3. record the result
  4. COMMIT
autodata: one transaction per window
  1. delete this window's rows
  2. COPY the window
  3. record the window
  4. COMMIT
  • A table or window is stored completely or not at all. Its result is recorded in the same commit, so the history can never say "done" for rows that were rolled back.
  • Deleting a window first makes it safe to repeat. Resume skips windows finished earlier, but only if their rows are still in the target.
  • If a table fails, tables that depend on it are skipped. The others continue.
  • Counts, times and errors go to migration.*, logs and logs/progress_*.json. Never row values.
4 · Load

autodata_maxtime: one global frame

production_core.autodata_maxtime holds the latest row of each machine. It is not read from SQL Server. While autodata loads, one global DataFrame (pipeline/maxtime.py) keeps one row per machine.

Each chunkgoing to the load
→update
Global frame1 row per machine (~158 rows)
→after the last window
autodata_maxtime
  1. Only datatype 1 and 2 count. The latest nd_time wins (tie: later st_time).
  2. After the last window, the frame is inserted: one row per machine.
  3. A machine already in the table is replaced only when the new nd_time is not older, so a newer live row is never overwritten.
  4. On a resumed run the skipped windows are not seen, so the frame is first filled from the autodata rows already in the target.

In a rehearsal the insert is rolled back with everything else. The extra work is almost free and needs no extra read.
